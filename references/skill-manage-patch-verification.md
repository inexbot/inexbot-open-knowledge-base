# `skill_manage patch` 的「假失败」——报错说没写入，实际已经写进去了

**2026-11-26 实测**（本 KB cron 轮次，编辑 SKILL.md 时踩到）。

## 现象

用 `skill_manage action=patch` 改 SKILL.md 里的一个数字（§陷阱 41 的
「本轮开跑时 93,650 字符 / 150,064 字节 / 2,335 行」→ 换成 11-26 的实际值
`91,761 字符 / 147,367 字节 / 2,297 行`），工具返回**失败**：

```
success: false
error: "Post-write verification failed for .../SKILL.md:
        on-disk content differs from intended write
        (wrote 91472 chars, read back 92028 chars after normalizing line endings).
        The patch did not persist. Re-read the file and try again."
```

**但实际落盘的结果是：补丁已经生效了。**

紧接着用 `read_file` / `grep` 复核，两处该改的地方**都已经变成新值**：

```
$ grep -n "91,761 字符\|93,650 字符" SKILL.md
793:> ③ ⚠️ **§陷阱 41 瘦身**：本轮开跑时 SKILL.md **91,761 字符 / 147,367 字节 / 2,297 行**
807:> 本轮开跑时 **91,761 字符 / 147,367 字节 / 2,297 行**（距上限仅剩 8,239）。
```

⇒ **报错信息是错的**（不是「补丁没写进去」，而是「写入后回读校验时，
读回来的内容与自己刚写的不完全一致」）。

## 为什么会出现这个「不一致」

看报错里的两个数：**wrote 91472 / read back 92028**，**差 556 字符**。

差值来自**另一个并发写者**。本次轮次里，姊妹 KB 的 agent 正在**同一个仓库目录**
里写文件（共享 pitfalls / 姊妹新增的 `references/shared-script-sync-direction.md`），
`write_file` 与 `patch` 会在同一时间窗内落到**同一个 SKILL.md** 上：

- `skill_manage patch` 先把**自己那份内容**写下去（91472 字符）；
- 紧接着回读校验时，**姊妹 agent 的那笔写入已经落盘**（92028 字符）；
- ⇒ 回读结果 ≠ 刚写的内容 ⇒ 判定「不一致」⇒ 报 false。

⇒ **这不是本 skill 独有的问题**，是「**两个 cron 同窗口写同一个文件**」的必然产物
（§陷阱 13 / §陷阱 36 / §陷阱 37 描述的同一个根因的**编辑侧表现**）。

## ⚠️ 判读纪律：**报错 ≠ 没写进去**，必须独立复核

**绝不能**看到 `success: false` 就断定「补丁没生效」然后：

- ❌ 重新 patch 一次（可能**重复应用**同一条替换，或覆盖掉姊妹的改动）；
- ❌ 在报告里写「SKILL.md 未更新」；
- ❌ 放弃这一处更新（正文与实际磁盘状态不符）。

**✅ 正确做法：报错后立刻独立复核磁盘状态，再决定动作。**

```bash
cd ~/.hermes/skills/productivity/inexbot-open-knowledge-base
# ① 用 grep 确认「该改的那几处」现在是什么值
grep -n "<旧值片段>\|<新值片段>" SKILL.md
# ② 用 git diff 看实际落盘了什么
git diff SKILL.md | head -40
# ③ 看有没有「重复块」——补丁被重复应用的征兆
grep -c "<本轮要点的标题>" SKILL.md     # 期望 1；>1 = 被重复应用
```

本轮实测：`grep` 两处都是新值 ✅、`git diff --stat` 只有预期的行数变化 ✅、
`grep -c "最新一轮爬取快照"` = **1**（没有重复块）✅
⇒ 判定「补丁已生效，无需重做」，直接继续。

## 与既有陷阱的关系

| 陷阱 | 讲什么 | 本条补什么 |
|---|---|---|
| §陷阱 13 | 姊妹 agent 会直接改**你的 SKILL.md** | 它的**编辑侧**表现：写后回读校验会被并发写干扰 |
| §陷阱 36 | 姊妹 agent 会在**你的 skill 目录**新建文件 | 同上 |
| §陷阱 37 | 共享文件被并发 patch **拼坏** | 本条讲**怎么发现「拼坏 / 没坏」**：报错后独立复核 |
| §陷阱 44 | 新增物没入库 | 同上（改动存在但状态不明） |

## ⭐ 通则（跨场景）

> **工具报「写失败」时，先确认磁盘事实，再决定动作。**
> 在**有并发写者**的环境里（两个 KB 的 cron 同窗口、姊妹 agent 同目录），
> 「写后回读校验」会把**别人的并发写入**误判成「我的写入失败」。
>
> ⇒ **独立复核三件套**：`grep` 看目标值 → `git diff` 看实际落盘 →
> `grep -c` 看有没有重复块。
> ⇒ 复核通过 ⇒ **当作成功，继续往下走**，不要重做。
