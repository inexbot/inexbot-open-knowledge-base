### ⚠️ 这个重构暴露了「增量爬虫的改名盲区」的一个**新变体**

SKILL.md 里记的改名盲区（2026-10-23）是「**zh 路径变了、en/kr 没变**」——

**en/kr 两个 locale 完全没有 `dev-rt`/`dev-wk` 条目**（实测 `dev-rt: 0 / dev-wk: 0`），
所以**没有出现「三语种自相矛盾」**。

**crawler 为什么能正确处理**（与 10-23 那个案例不同）：

- 侧边栏（sidebar）里出现的是**新路径** `04.dev-wk` / `05.dev-rt` ⇒ 新 slug 的
  `raw/` 与 `md/` 都不存在 ⇒ 触发**真实抓取**；
- 旧路径 `04.dev-rt` **不再出现在 sidebar 里** ⇒ 增量爬虫**不会**再抓它
  ⇒ 旧条目**自然从 index.json 中消失**（本轮 index 里 `dev-rt` 只剩 `05.dev-rt` 的 72 条，
  `04.dev-rt` 的 73 条**已不在 index**）。

⇒ **结论：这次的重构处理得是对的**，不需要「精准失效缓存」那套操作

### ⚠️ **引用链接 404 的成因与判读（本轮踩到，值得记）**

**本轮开跑时**（爬取**之前**）跑 `check_citation_links.py` → **7 条 404**，
全部在 `/zh/05.JSON-协议/04.dev-rt/` 下。

**当时的直觉判读会踩坑**：以为「上游又收紧 URL 形态」或「引用链接机制坏了」，
于是想「按 KB 分派做全套修复」——**这是错的**。

**正确判读顺序**（本轮实测得出）：

1. **先看 404 路径的前缀** —— 7 条全在同一个一级分区 `04.dev-rt` 下
   ⇒ **不是「URL 形态」问题（那会全站随机 404）**，是「**某个分区整体失效**」。
2. **交叉验证**：`grep "✓" 日志` → 本轮新抓的路径里出现的是 **`04.dev-wk`**，
   **完全没有 `04.dev-rt`** ⇒ 上游把这一分区**改名**了。
3. **实网打旧路径** → **404 确认**上游确实删了。
4. **爬完再跑一次** → **60/60 全 200** ✅。

⇒ **最终 7 条 404 是「爬取前 index 里还留着旧路径」的必然中间态**，
**爬取完成即自愈**。**判据：`404` 若集中在少数前缀 → 先怀疑「上游改名/删页」，
而不是「URL 形态收紧」**（后者是全站性的）。
