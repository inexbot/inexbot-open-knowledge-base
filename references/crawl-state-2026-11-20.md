## 五、本轮修复：`check_url_to_index_key.py` 的「死代码」缺口

**背景**：11-19 姊妹 KB 为「上游改 URL 形态」重写了归一化逻辑，
新增 `norm_key_candidates()`（处理目录页 key 带尾斜杠 `/zh/` 的情形）——
**但那个函数从头到尾没有接进主循环**，是**死代码** ⇒ 目录页必然 miss。
11-19 报告里「候选 key 修复刚写入，尚未验证（此前 92/93，漏的是根目录页）」正是这个缺口。

**本轮动作**（本库副本从 11-09 的旧版移植到姊妹 11-19 版 + 接线修复）：

1. 归一化**按 KB 分派**（姊妹 11-19/11-10 修正）：
   - `inexbot`（key 已 percent 编码）：只把 url 里的 `%26`→`&`、`%2B`→`+`，**中文那半边的 `%XX` 原样保留**；
   - `inexbot-open`（key 是明文中文）：url 是整体编码态 → 需**整体 `unquote()`**。
   - ⚠️ 用同一条规则套两个 KB → 必然大面积**假 miss**（看着像 KB 回归，实为脚本自伤）。
2. **剥 URL 后缀**：`inexbot` 侧 url 现在带 `.html` / `/index.html`，必须先剥再查表。
3. **接线 `norm_key_candidates()`**（本轮新增）：目录页同时试「带尾斜杠」和「不带尾斜杠」两种形态。

**修复前 → 修复后**：

| | 修复前 | 修复后 |
|---|---|---|
| URL→index-key hit | **1 / 93** | **93 / 93** ✅ |
| no-md lookup | 92 | **0** ✅ |
| 静默降级(==800) | 0 | 0 ✅ |

**判读陷阱复盘**：修复前那个「1/93」曾看起来像 KB 回归；
实为**审计脚本自己的查表 bug**（与共享 pitfalls §陷阱 24/25 同族）。
假阳性指纹：**只有个位数条目报缺**（真·slug 契约断裂的特征是 0/N + 孤儿=全量）。

> 💡 **通用教训（共享 pitfalls 陷阱 40）**：**辅助函数「定义了但没接进调用链」**
> ⇒ 修复**写了却没生效**，而且**没有任何报错**。
> 本轮的具体表现：姊妹 11-19 的 `norm_key_candidates()` 定义得好好的，
> 却从未在 `main()` 里被调用 ⇒ 目录页的 key 永远还原不出来。
> **⇒ 移植别人脚本后，必须验证「新函数真的被调用了」**，
> 最直接的验证就是看**修复前后的数字有没有变**（本轮 1/93 → 93/93）。
> 只看「函数存在」「语法通过」是不够的。
